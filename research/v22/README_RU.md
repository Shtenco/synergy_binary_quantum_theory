# БКГ V22 — оригинальная C1-цепочка, глубокая локальная проверка

Версия: 2026-11-08. Полная физическая лоренцева пара и HDA **не рассчитаны**.

## Непосредственно найденные ошибки V21

1. В V21 collection при обращении к настоящим V2-амплитудам использовалось несуществующее имя `source`; выполнение дошло бы до `NameError` после дорогостоящего прохода. Исправлено на `s` — физический узел текущей пары.
2. V21 проверял каждый NPZ в отдельности, но не хеш-связь между двумя последовательными стадиями. Исправлено: стадии 2 и 3 теперь записывают `predecessor_npz_sha256` и `predecessor_metadata_sha256`; коллектор проверяет обе связи для всех 32 путей.
3. V21 употреблял пороговое сложение `W.add()` после каждого вспомогательного канала. Это могло преждевременно уничтожить малые комплексные слагаемые до когерентной суммы. V22 суммирует 8 сложных состояний через `math.fsum` по вещественным и мнимым частям, без промежуточного фильтра по амплитуде. Подчеркнём: внутренние пороги самого original SU(2) backend не изменены и требуют отдельного бюджета погрешностей.
4. V2-файлы с корректными SHA могли принадлежать другой версии оператора. Введён отдельный скрипт, вызывающий оригинальный `pl_lorentzian_triple_worker.run()` под исходным tetrahedral backend, и проверка commit SHA, backend SHA, индекса ориентации, режима, `checks` и ссылки на NPZ.
5. Файл со словом `passed=true` сам по себе не является независимым криптографическим доказательством происхождения. Доверие к вычислительному окружению и журналам сохраняется как открытая инфраструктурная предпосылка.

## Исполнитель одной настоящей пары

Скрипт `pl_v22_one_pair_runner.py` предназначен для **полного checkout** оригинального приватного репозитория. Для одной выбранной `(source,omit,cycle)` путь 

- 32 конечных `3-leg` вспомогательных состояния.
- 12 **различных** первых операторных вызовов (настоящие сигнатуры C(V)/C(K)).
- 32 вторых и 32 третьих вызова: 76 вместо 96 без кэша.
- 4 дополнительных независимых производственных V2-примитива.

Эта экономия касается количества вызовов, а не гарантированного ускорения во времени.

Команда из корня рабочего checkout (поместить скрипты в `scripts/`):

```bash
python scripts/pl_v22_one_pair_runner.py --source 0 --omit 0 --cycle 0 --max-new 1 --out out/bqg_v22_pair_0_0
```

`--max-new 1` — ограниченный диагностический запуск, а не закрытая пара. Для продолжения использовать тот же `--out` и такой же SHA коммита, а при достаточных вычислительных ресурсах убрать `--max-new`. При успешном вычислении всех 32 путей сценарий требует независимо завершённых оригинальных V2 и собирает полную пару.

Не следует менять код после создания checkpoint, иначе их источник SHA изменится. Все тесты и операторы должны запускаться с одного зафиксированного SHA и соответствующего volume backend.

## Локальная проверка (модельные входы, не SU(2) физика)

```bash
python -m unittest -v test_v20 test_v21 test_v22_e2e test_v22_runner
```

56/56 тестов PASS на модельных данных, включая положительный полный программный 32-путевой проход и отрицательные случаи пропуска одного пути, несоответствия SHA, ошибки в V2, неправильной метадаты и повреждения цепочки предшественников. Программные тесты намеренно **не признаются настоящими физическими амплитудами**.

## За пределами результата

- C1 физически: 0/32 новых завершающих истинных путей в данном локальном проходе (оригинальный production backend не был смонтирован в локальном вычислительном контейнере).
- В2/В4: для оригинальной пары независимое численное совпадение не измерено.
- C2: единый оператор H_E+H_L+R и физическое ядро не получены.
- C3: нет независимого физического D, полного off-shell HDA, континуального предела, положительного TT-полюса.

**Этот архив — инженерная подготовка воспроизводимых вычислений, а не доказательство БКГ.**
