# W5 → Lorentzian: аудит первичного KKV-конвейера и адаптер j=2

Дата: 2026-11-10

## 1. Важная находка: старый Lorentzian runner вычислял не тот входной сектор

В исходной ветке `research/bqg-v04-actual-constraint-kernel-20261106` обнаружен `scripts/bqg_v08_lorentzian_24term_raw_column.py`.

Его вход создаётся так:

```python
ini = PW.basis_full_jhalf()[index]
```

То есть этот runner работает с all-`j=1/2` граничным состоянием, а не с W5, использованным в евклидовом сертификате. В евклидовом W5 исходные ключи имеют вид:

```python
((4,) * 10, (K, 0, 0, 0, 0)),  K in (0,2,4,6,8)
```

Здесь doubled spin 4 означает физический (j=2) на каждом из десяти рёбер K5. Поэтому результаты all-`j=1/2` Lorentzian runner нельзя подставлять в W5 Gram. Это разные входные пространства.

## 2. Второй важный разрыв: cutoff

Старый runner устанавливает `Jmax2=7`, то есть (J_{max}=7/2), и документирует этот cutoff как стенку для all-`j=1/2` single-(H_L) расчёта. Для W5 с начальными рёбрами (j=2) этот cutoff не обоснован.

Новый W5 adapter требует как минимум `Jmax2=10` ((J_{max}=5)) как консервативную начальную стенку, но это ещё не доказательство сходимости. Настоящая проверка должна сравнить результаты при возрастающих cutoff, например 10, 12, 14, и подтвердить, что амплитуды W5-выхода и малые сингулярные числа стабилизировались, а leakage не скрыт обрезанием.

## 3. Что уже существовало

Исходный Lorentzian pipeline уже имеет:
- sine-Hermitian (H_E^{sine}=(T-T^dagger)/(2i));
- (K_{sine}=[V,H_E^{sine}]);
- covariant (C_e(V)) и (C_e(K));
- state-to-state ordered triple (mathrm{Tr}_{aux}[C_a(K)C_b(K)C_c(V)]);
- epsilon expansion в 24 упорядоченных K-K-V тройки.

Но исходный код прямо предупреждает, что 24-term output — raw structural amplitude: без Hermitian completion, без полного физического (H_L) и без prefactor.

В одном старом Actions run (42253078812) евклидовый W5 job завершился успешно, а raw Lorentzian all-(j=1/2) job был отменён во время шага 24-term calculation. Лог не содержит завершённого первого epsilon term. Это не физический нулевой результат, а незавершённое вычисление.

## 4. Новый W5 adapter

Добавлены:
- `scripts/bqg_v09_w5_lorentzian_raw_column.py`
- `tests/test_bqg_v09_w5_lorentzian_raw_column.py`

Новый runner:
1. использует ровно пять входов W5 из евклидова сертификата;
2. вычисляет евклидову sine-ordered колонку (A_v) на том же входе;
3. вычисляет сырую когерентную 24-term KKV колонку (B_v^{raw}), не заменяя сумму нормами отдельных членов;
4. требует скалярного замыкания после auxiliary trace;
5. переводит конечный (J=0) covariant key обратно в тот же Gauss output-key формат;
6. сохраняет полные комплексные sparse amplitudes, а не только нормы.

Пример для одного столбца:

```bash
python scripts/bqg_v09_w5_lorentzian_raw_column.py \
  --node 0 --input-K 0 --Jmax2 10 --start 0 --count 24 \
  --output verification_results/W5_L_K0_NODE0.json
```

## 5. Почему пока нельзя объявить совместное ядро

Даже после вычисления всех сырых (B_v^{raw}) останутся две отдельные обязательные задачи:

**Hermitian completion.** Сырой epsilon-KKV блок в исходном коде явно не является финальным Hermitian (H_L). Нужно построить adjoint-consistent оператор, а не называть raw map полным (H_L). Для этого надо либо реализовать доказанную симметризованную ordering формулу на уровне операторов, либо вычислить достаточно полный набор обратных матричных элементов, чтобы проверить и построить adjoint.

**Физическая нормировка.** В сыром KKV нет фиксированного ((1+\beta^2))-множителя и общих (kappa,hbar)/регуляторных коэффициентов. Их нужно брать из единого convention ledger, не подбирать по спектру.

Только после этого строится:
[
G_{EE}=A^\dagger A,\quad G_{EL}=A^\dagger B,\quad G_{LL}=B^\dagger B
]
для полного Hermitian (B), а затем Gram полной суммы.

## 6. Текущий статус

**Сделан существенный методологический шаг:** обнаружено и устранено концептуальное несоответствие входного сектора между предыдущим Lorentzian runner и W5 евклидовым сертификатом. Новый код уже адресует именно W5 (j=2) входы.

**Не сделано:** полный численный W5 Lorentzian прогон, Hermitian completion, cutoff convergence и физическая joint-kernel проверка. Ни один из этих результатов не заявляется до выполнения соответствующих тестов.
